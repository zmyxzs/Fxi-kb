# 11 风险、技术决策与长期防范备忘

> 状态：`CURRENT + PLANNED`
## 当前关键技术决策（已冻结）

| 决策主题 | 最终决断 | 核心理由 |
|---|---|---|
| **真理源归属** | **纯文本优先（Text-First）**：Markdown + YAML Frontmatter 为单真理源；SQLite 为衍生加速索引 | 彻底防范 5 年长期项目数据库损坏、工具迁移或 Schema 锁死导致的资产覆灭 |
| **产品形态** | 本地优先、无重型 UI、CLI + 统一本地 JSON API | 专注底层数据可靠性与写作人机工效，杜绝过早背负桌面/Web 端维护包袱 |
| **全文检索** | **Python jieba 结合项目专有词典 + SQLite FTS5** | 绕过 Windows C 编译依赖，根治中文网络小说专有名词切词破碎的致命问题 |
| **项目隔离** | 强制作用域查询；**引入分歧点（POD）与后分歧点继承过滤** | 解决同人创作中后期原著动态剧情事件污染 AU 时间线的核心痛点 |
| **认识状态** | 命题四层模型（`proposition` / `assertion` / `judgement` / `evidence`） | 彻底解耦实体、主张属性、角色谎言、读者误解与推翻关系 |
| **时空建模** | **时间区间有效性（`valid_from` ~ `valid_to`）与因果 DAG** | 避免 $N \times M \times K$ 笛卡尔积状态组合爆炸，优雅支持插叙与倒叙 |
| **数值与战力** | **动态状态账本（State Ledger）**：定义 + 变动事件 + 时间点快照 | 杜绝直接记录孤立静态数字，支持中途修改剧情后的余额自洽重算 |
| **审核机制** | **按需惰性抽取（Lazy Extraction）+ 提议分级分流（Triage）** | 防止 100 万字原著产生数万条 proposal 导致作者审核疲劳与系统弃坑 |
| **生命周期** | **四级删除语义**：`exclude` / `disable` / `supersede` / `purge` | 杜绝单点误删导致历史引用悬空，任何物理清理前强制执行影响分析 |
| **文风闭环** | 生成上下文快照 + **反面教条（anti-pattern）** + Canary 金丝雀分流回滚 | 允许试错，快速熔断劣质文风，通过负面约束纠偏模型行文恶习 |
| **向量增强** | 首选本地 Qwen3-Embedding-0.6B，BGE-M3 作对照；混合 RRF 重排 | 保护创作隐私，断网可用，且索引随时可依据原文无损全量重建 |
| **章节稳定性** | **语义场景 UUID（`scene_uuid`）作为全系统因果与时序锚点** | 彻底解耦物理章节号变动；作者插章、删章或重排时，伏笔与账本关联绝不断链 |
| **视点防穿帮** | **视点过滤器（`pov_character_id`）物理阻断不可知信息** | 杜绝反派或配角视角写作时，AI 检索带入主角机密底牌造成“全知视角穿帮” |
| **合法吃书** | **追溯性修正事件（`retcon`）** 解构“旧主张+新主张+过渡提示” | 支持作者主动改动早期设定，豁免 OOC 误报并自动在写作时提供吃书过渡提示 |
| **半途接入** | **三态数值模型（`EXPLICIT`/`UNMEASURED`/`NOT_APPLICABLE`）+ 基准锚点** | 解决写到第 50 章才想统计金币/战力的场景，无需往前逐章补录历史，零透支误报 |
| **算力与显存** | **本地 RTX 2060 6GB 显存红线守卫 + 2500~4000 Token 上下文预算** | 本地仅常驻 0.6B Embedding（~1.5GB），严禁并发大模型防 OOM，抽取生成走低成本云端 API |
| **模型管理与网关** | **全库统一网关（`model-gateway`）+ 提示词外部化（`prompts/`）** | 集中处理任务分级路由、JSON 容错修复、哈希调用缓存与记账；严禁业务模块各自散落写 HTTP 调用 |
| **外部集成** | `novel-Skill` 默认只读；写回必须走显式提议（`propose`）接口 | 严格防范外部 Agent 把未经验证的脑洞或幻觉写死进正式库 |

## 核心系统风险与深度防范措施

### 1. 人工审核疲劳（Review Fatigue，长期项目第一死因）
- **风险**：整本导入长篇小说后，AI 抽取产生海量 candidate claims，作者在 CLI 下疲于确认，最终要么放弃使用，要么机械全选接受摧毁数据质量。
- **防范**：
  - 严禁全书无差别自动抽取，推行“按需惰性抽取（Lazy Extraction）”；
  - 引入“提议自动分流”：单纯的原文引用且无冲突项自动标记 `auto_accepted`，仅将高危 AU 规则、角色性格反转列为待审。

### 2. 中文分词失真与生僻名词断词
- **风险**：SQLite 默认分词器将中文切成单字或乱切词，搜修仙法宝或玄幻人名产生大量无关噪音或漏搜。
- **防范**：
  - 应用层在分词前，动态将所有人物名、宗门势力、法宝功法导出生成 `project_lexicon.txt`；
  - jieba 强制优先匹配专有词典后再写入 FTS5。

### 3. 同人创作中后期的“蝴蝶效应污染”
- **风险**：同人救下了本该阵亡的角色，但在写到后续剧情时，系统把原著第 20 章该角色的葬礼当成权威事实召回，导致逻辑冲突。
- **防范**：
  - 在同人项目设定中锚定分歧点（POD）；
  - 检索器自动切断分歧点后原著的“动态情节与事件事实”，仅继承“静态世界观与地理法则”。

### 4. 状态组合爆炸（Combinatorial Explosion）
- **风险**：每个角色在每个章节显式存一份状态快照，数据表体积快速飙升到数千万行。
- **防范**：
  - 采用区间有效性（`valid_from` ~ `valid_to`）与惯性继承，只有发生变更才写入新事件；
  - 状态快照作为按需计算的派生缓存。

### 5. 数据库损坏与 Schema 升级锁死
- **风险**：自用系统在未来数年内多次重构表结构，或 SQLite 发生低概率损毁，导致多年积累的世界观资产尽失。
- **防范**：
  - 彻底践行“Text-First”设计：所有世界观对象以 Markdown 文件为主体；
  - SQLite 纯粹是可随时丢弃并重建的索引层，任何崩溃只需一条 `kb rebuild` 即可瞬间恢复。

### 6. 上下文注意力稀释（Lost-in-the-Middle）与 Token 浪费
- **风险**：生成时一股脑把 10 条原著、5 篇文风、战力属性全塞进 Prompt，导致模型抓不住当前场景的核心戏剧冲突，且大幅增加 API 延迟与调用费用。
- **防范**：
  - 实施场景化上下文剪枝（Context Pruning）：打斗场景剔除环境文风，对话场景剔除战力数值；
  - 设定 2500~4000 tokens 黄金预算上限，按优先级截断并动态压缩低权数据。

### 7. 作者主动“吃书”引发全书 OOC 警报雪崩（Retcon Collapse）
- **风险**：长篇写作中作者常根据创作灵感追溯修改早期设定（如第 50 章改口说主角其实是半妖），若按传统严格冲突校验，系统会在全书报出数百处严重逻辑冲突，导致辅助功能瘫痪。
- **防范**：
  - 引入显式 `retcon` 追溯性修正事件机制；
  - 一旦登记 Retcon，OOC 扫描器豁免针对该旧设的冲突报警，并在后续写作时输出“吃书过渡提醒”（如提示作者在此处添加角色内心独白或震惊揭示以掩盖生硬感）。

### 8. 章节增删与重排引发关联引用断裂（Renumbering Fragility）
- **风险**：网络小说连载期作者常在中间插入“过渡章”或“加更”，物理章序号全部后移（原第 15 章变成第 16 章），导致所有按物理章号记录的伏笔与账本索引全部错位悬空。
- **防范**：
  - 严禁任何数据库外键绑定物理章节号（`chapter_15`）；
  - 全面使用语义场景 UUID（`scene_uuid`），物理章节号仅作为导入时动态计算的视图展示层。

### 9. 视点穿帮与偷看剧本（POV Perspective Leaks）
- **风险**：作者以反派配角 POV 展开场景描写时，系统检索注入了主角的隐藏法宝或真实身份，导致模型输出“反派居然在心里忌惮主角还未展现的秘法”，毁掉悬念与代入感。
- **防范**：
  - API 检索层强制支持 `pov_character_id`；
  - 对召回的所有事实、能力与事件进行视点认知状态强校验（`is_known_by(pov_char)`），凡观察者不可知的隐藏情报在上下文组装前彻底物理剔除。

### 10. 本地硬件显存溢出（VRAM OOM Crash）
- **风险**：创作者个人电脑搭载 RTX 2060 (6GB VRAM)，若盲目尝试本地部署 7B/14B 生成大模型并同时加载 Embedding 向量模型，极易导致显卡驱动崩溃、蓝屏或推理卡死。
- **防范**：
  - 显存严格配额制：本地仅常驻运行 Qwen3-Embedding-0.6B（FP16 显存仅需约 1.5GB）；
  - 复杂的关系抽取、OOC 检查与大段正文辅助生成走高性价比云端 API（如 Gemini Flash / DeepSeek）；
  - 本地与云端解耦，确保离线模式下纯文本 FTS5 搜索与基础账本重算照常极速运行。

### 11. 大模型 API 样板代码膨胀与供应商绑定（API Boilerplate & Vendor Lock-in）
- **风险**：抽取、审核、摘要、素材提炼等多个模块到处散落手写 HTTP 请求、重试和鉴权逻辑；一旦供应商调整价格或接口下线，全库代码大范围瘫痪。
- **防范**：
  - 建立统一的 `model-gateway`；
  - 以 OpenAI 兼容协议为核心，声明式配置 `models.yaml` 映射任务与模型，业务代码仅传任务名，无感切换任意云端/本地大模型。

### 12. 大模型输出格式畸变导致知识库入库崩溃（JSON Parse Collapse）
- **风险**：大模型偶尔输出 markdown 语法块、未闭合花括号、多余逗号或解释性废话，导致 `json.loads` 抛出异常，批处理抽取任务意外中断。
- **防范**：
  - 网关建立“三道防线”容错管道：Markdown 围栏剥离 $\rightarrow$ `json_repair` 自动修补 $\rightarrow$ Pydantic Schema 强校验；
  - 校验失败自动触发 1 次带有错误原因的 1-Shot 自动修正重试，彻底杜绝数据中断。
