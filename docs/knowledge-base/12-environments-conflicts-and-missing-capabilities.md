# 使用环境、冲突控制与能力边界

## 结论

知识库最需要防范的不是“没有更多 AI 能力”，而是不同使用环境把内容写到错误的范围，或者把一个临时判断误升级成全局事实。

因此系统应遵循四条原则：

1. **查询默认只读**：搜索、召回和生成上下文不能修改知识库。
2. **项目默认隔离**：不同作品、AU、版本和草稿不能互相污染。
3. **AI 结果默认是提议**：外部或本地模型的分析必须可追溯、可推翻、可审核。
4. **事实不覆盖，只产生新版本**：冲突内容保留来源和历史，通过状态、时间和适用范围解决。

## 一、需要区分的使用环境

| 环境 | 主要内容 | 默认权威性 | 默认写入方式 |
|---|---|---|---|
| 原作/外部来源 | 原始 txt/md、章节、对白、设定集 | 对“原作写了什么”最权威 | 导入新版本，不直接改原文 |
| 同人项目 | 项目设定、AU、改写后的关系和时间线 | 对当前项目最权威 | 可修改，但只限当前项目 |
| 原创作品 | 自己确定的世界观、人物和草稿 | 对当前原创项目最权威 | 项目内维护 |
| 写作知识 | 文笔、叙事、节奏、人物塑造方法 | 对写作建议有参考价值 | 经过整理后共享 |
| 创意素材 | 金手指、套路、灵感、优秀片段分析 | 不是故事事实 | 作为素材或候选方案 |
| 当前草稿/写作会话 | 正在写的章节、临时构思、试验性改动 | 只对当前写作状态有效 | 先保存为草稿或候选 |
| AI 分析区 | 自动抽取、摘要、推理和矛盾报告 | 不能自动成为权威 | 待审核记录 |
| 派生索引 | FTS、embedding、摘要缓存、关系图缓存 | 没有独立事实权威 | 可删除并重建 |

这里的“权威”必须带范围。例如，原作可以决定“原作中发生了什么”，但不能阻止同人项目明确写出“本项目从第 12 章开始改变这件事”。

## 二、最常见的环境冲突

### 1. 原作事实和同人设定冲突

不要把同人设定改写进原作资料。应保留：

- 原作主张：适用于原作世界线；
- 项目覆写：适用于指定项目和指定版本；
- 两者之间的关系：`overrides`、`diverges_from` 或 `alternative_to`。

查询当前同人项目时，返回项目设定优先，同时保留原作依据，让写作者知道偏离发生在哪里。

### 2. 三个写作项目互相污染

每条项目数据必须绑定：

- `project_id`；
- `world_id` 或 `timeline_id`；
- 可选的 `work_id`、章节和版本；
- 来源类型：原作、项目设定、草稿、素材。

默认查询只使用当前项目和明确共享的只读来源。不能因为角色名、物品名或标签相同就自动跨项目合并。

### 3. AI 推测覆盖已确认内容

自动抽取的内容应进入 `proposal` 或 `analysis` 状态，而不是直接写入 `accepted_fact`。每条分析至少保存：

- 使用的模型和版本；
- 提示词或分析任务版本；
- 输入来源和定位；
- 产生时间；
- 置信度；
- 支持和反驳证据；
- 审核人和审核结果。

模型可以提出“可能是某人的化名”，但不能未经确认就把两个角色合并，也不能删除与之冲突的旧判断。

### 4. 草稿中的临时设定变成正式设定

写作时经常会先试写一个能力、关系或剧情走向。它应先标记为：

```text
draft_idea → candidate_setting → accepted_setting
                         ↘ rejected / superseded
```

只有用户确认或明确提交后，才进入项目的正式设定。否则下一次检索可能把作者自己尚未决定的想法当成确定事实。

### 5. 修改原文后派生数据过期

原始 txt/md 修改后，旧的切片、embedding、摘要、事实抽取和关系图都可能不再匹配。每个派生结果应记录：

- `source_revision_id`；
- 切片规则版本；
- 模型和 embedding 版本；
- 生成时间；
- 当前状态：`fresh`、`stale`、`rebuilding`、`failed`。

系统应能发现过期并重建，不能静默使用旧索引。

### 6. 不同模型得出不同判断

不同模型的结果应作为不同的判断来源，而不是互相覆盖：

```text
同一个问题
  ├── 本地模型判断 A
  ├── 外部模型判断 B
  └── 人工确认或保留争议
```

如果无法判定，应明确显示“存在多个解释”，而不是选一个看起来最像答案的结果。

### 7. 角色认知和作者视角混淆

作者知道的内容、读者已经知道的内容、角色知道的内容必须分开。写作调用时要按场景时间过滤：

- 角色当时知道什么；
- 角色当时相信什么；
- 读者此时知道什么；
- 作者后台知道什么。

否则检索很容易把真相直接提供给角色，造成 OOC 或悬念泄露。

## 三、写入权限应该分级

即使是个人自用，也建议把能力分为四级：

### `query`

只读查询、全文搜索、向量检索、时间线查询、冲突报告和上下文打包。`novel-Skill` 主要使用这一层。

### `propose`

创建待审核的事实、人物关系、摘要、风格分析或项目设定。可以写文件或数据库，但不能改变正式内容的状态。

### `commit`

确认、驳回、替代、合并或拆分知识条目。这个能力应由用户通过 CLI 或明确操作触发，不应在普通生成请求中自动执行。

### `admin/rebuild`

导入新来源、删除或归档项目、迁移数据库、重建索引和备份恢复。它应与普通检索、写作生成分开。

建议：`novel-Skill` 默认只有 `query`，必要时可以使用 `propose`；不直接拥有 `commit`、删除或迁移权限。

## 四、推荐的状态和版本机制

### 1. 不删除有意义的旧判断

当新证据推翻旧判断时，不要直接覆盖文本。建立新记录并关联：

```text
旧主张 ──superseded_by──> 新主张
旧主张 ──contradicted_by─> 新证据
旧主张 ──valid_until─────> 某个时间或版本
```

这样可以回答“以前为什么这么判断”“是哪条证据推翻的”。

### 2. 事实状态和适用范围分开

不要只使用一个 `true/false` 字段。至少要区分：

- `supported`：当前证据支持；
- `inferred`：推断而非原文明确；
- `uncertain`：尚未解决；
- `contradicted`：存在反驳；
- `rejected`：人工否定；
- `superseded`：被新版本替代。

同时记录它适用于哪个作品、项目、世界线、章节或时间区间。

### 3. 读写操作分离

查询接口不能隐含执行“自动整理”或“顺便入库”。推荐把操作明确分为：

```text
search / retrieve / inspect       只读
extract / analyze / suggest       产生候选
accept / reject / supersede       改变知识状态
reindex / backup / migrate        管理派生数据或系统
```

## 五、哪些能力不应该放入知识库

### 不应该由知识库负责的业务能力

- 当前章节如何写、如何续写；
- 提示词怎样组织和迭代；
- 生成文本的模型选择和调用流程；
- `novel-Skill` 的章节状态、生成循环和风格执行策略；
- 自动决定剧情走向；
- 自动判断某个同人项目是否“应该”遵守原作；
- 用户确认、撤销和最终创作取舍。

这些属于 `novel-Skill` 或用户控制的写作流程。

### 不应该作为知识内容存储的东西

- API 密钥、访问令牌和登录信息；
- 临时提示词、临时上下文和 token 缓存；
- 不带来源的模型结论；
- 仅用于加速的 embedding、摘要和索引缓存；
- 运行日志中的隐私信息；
- 某个模型的内部状态或权重；
- 其他项目未明确授权共享的草稿和私人资料。

作品草稿本身可以由知识库保存和索引，但应作为项目文档/来源保存，不能因为它被索引就自动变成正式事实。

## 六、目前还欠缺的关键能力

现有规划还需要明确补齐以下能力：

1. **范围上下文**：每次查询必须带项目、作品、世界线、版本和资料类型；
2. **来源快照**：保存原始文件的版本、哈希和稳定定位；
3. **提议审核流**：AI 抽取、摘要和推理不能直接成为正式知识；
4. **冲突中心**：可以列出冲突主张、证据和待处理状态；
5. **可回滚历史**：支持查看、恢复和比较旧版本；
6. **派生数据失效检测**：原文、切片规则或模型变更后标记索引过期；
7. **安全写入边界**：区分 query、propose、commit 和 admin；
8. **备份与导出**：至少可以导出 Markdown、JSON 和 SQLite 备份；
9. **检索质量测试**：用固定问题检查是否召回了正确项目和正确证据；
10. **失败可见**：模型调用、解析、索引或迁移失败必须记录并报告，不能静默返回空结果；
11. **敏感资料隔离**：不同目录、项目和外部模型之间明确控制哪些内容可以发送；
12. **模型无关的数据格式**：换 embedding 或大模型时，原始资料和主张不应丢失。

## 七、建议的目录和数据流

```text
sources/       原始 txt/md 和版本快照，只追加新版本
projects/      各作品、AU、草稿和项目设定，互相隔离
knowledge/     已确认的对象、主张、时间线、关系和认知状态
proposals/     AI 分析、待审核事实、候选设定和冲突报告
materials/     通用写作知识、风格资料和创意素材
derived/       FTS、embedding、摘要和关系图缓存，可重建
backups/       手动或定期备份
```

```text
导入来源
  → 版本化原文
  → 解析/切片
  → AI 或人工产生候选
  → 审核
  → 正式知识或项目设定
  → FTS/embedding 等派生索引
  → novel-Skill 按范围只读调用
```

## 八、最低可行的防错方案

在没有 UI 的前提下，第一版也应实现：

- 每条内容都有唯一 ID、项目范围、来源和版本；
- 原始 txt/md 不被自动覆盖；
- AI 输出写入 `proposals`，不直接写入正式事实；
- `novel-Skill` 查询必须带 `project_id`；
- 正式修改使用显式 CLI 命令，并生成历史记录；
- 原文修改后旧索引标记为过期；
- 可以输出当前项目的冲突清单和待审核清单；
- 可以从 Markdown/JSON/SQLite 备份恢复。

这些能力比一开始加入更多模型、自动推理或复杂 Agent 更重要。

## 一句话判断

知识库应当是“有范围、有来源、有版本、可追溯的事实和素材存储与检索系统”，而不是自动替所有使用环境做决定的全能大脑。环境之间通过明确的项目范围、权限和版本关系协作，才能避免一次错误分析修改整个系统。
