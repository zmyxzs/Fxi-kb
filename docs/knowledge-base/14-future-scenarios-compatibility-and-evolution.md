# 后期使用场景、兼容性与系统演进

> 状态：`PLANNED`
## 1. 为什么现在就要考虑演进

知识库最初可能只是“导入 txt/md 并搜索”，但写正文后很快会出现：

- 统计角色拥有的金币、物品、资源和战力；
- 查询某一章开始时角色的状态；
- 修改或删除错误的风格分析和素材；
- 更换 embedding、大模型、切片规则或存储方式；
- 同一资料由 CLI、`novel-Skill`、批处理脚本和未来 UI 同时使用；
- 原作出现新证据，推翻之前的猜测；
- 分支世界线、时间回溯和多版本草稿并存。

如果第一版把“当前值”“AI 结论”“检索缓存”和“正式事实”混在一起，后期兼容会非常困难。因此从第一版就要区分：

```text
核心数据：原始来源、用户确认的项目设定、正式主张、事件记录
候选数据：AI 分析、临时构思、未确认风格判断
派生数据：摘要、切片、FTS、embedding、状态快照、统计结果
运行数据：当前会话、提示词、模型调用状态、缓存
```

只有核心数据需要长期兼容；候选数据需要可审核；派生和运行数据必须可以失效、删除和重建。

## 2. 场景与应对模块

| 后期场景 | 主要风险 | 应对能力 |
|---|---|---|
| 正文中统计金币和资源 | 只保存一个当前值，无法解释变化 | 事件账本、时间点状态、单位和来源 |
| 中途才开始统计数值（第50章才算金币） | 往前推算导致历史章节频繁触发“透支/未定义”报错 | **三态数值模型**（`EXPLICIT`/`UNMEASURED`/`NOT_APPLICABLE`）+ **基准锚点**（`baseline_anchor`） |
| 计算战力 | 战力定义变化，旧结论全部失效 | 多维指标、规则版本、测量时间 |
| 角色获得/失去能力 | 章节前后能力穿越 | 能力状态事件、有效区间、前置条件 |
| 作者主动修改旧设定（吃书） | OOC 扫描器在全书报出上百处旧设冲突瘫痪系统 | **合法吃书（`retcon` 追溯性修正事件）**，豁免冲突误报并生成叙事过渡提示 |
| 章节插入/删减/重排 | 物理章号整体偏移导致历史引用、伏笔、账本全部错位断链 | **语义场景 UUID（`scene_uuid`）解耦物理章号**，章号仅作为动态计算视图 |
| 配角/反派 POV 视点写作 | 检索注入了主角未公开的底牌，导致模型替反派开全知透视挂 | **视点过滤器（`pov_character_id`）**，在组装 Prompt 前物理剔除不可知情报 |
| 风格学习效果差 | 错误风格判断污染所有项目，模型越写越油腻 | 风格版本、评测集、**反面教条（anti-pattern）**、Canary 分流、禁用和回滚 |
| 删除错误内容 | 引用悬空、索引残留、模型仍召回 | 生命周期、影响分析、四级软删除和一键重建 |
| 多版本情节走向试写（草稿分支） | 废案与正文混杂，伏笔与状态相互踩踏 | **草稿分支（`draft_branch`）机制**，支持在独立世界线推演，不污染主线 |
| 新增一种资料或流程 | 数据库和 API 被迫大改 | 扩展字段、类型注册、版本化契约 |
| 本地硬件限制（RTX 2060 6GB）与成本 | 显存 OOM 崩溃、云端 Token 消耗失控与延迟严重 | **显存严格配额（本地仅常驻 1.5GB Embedding）+ 2500~4000 Token 黄金预算剪枝** |
| 多工具同时操作 | 覆盖修改、项目串线 | revision、乐观并发检查、权限边界 |
| 分支/AU/重置时间线 | 不同世界线互相污染 | world、timeline、branch 和 **分歧点（POD）过滤** |
| 外部模型处理私人草稿 | 隐私泄露和资料越界 | 发送策略、脱敏、provider 记录和本地优先 |
| 长期停用或迁移系统 | 数据被系统锁定 | **纯文本第一公民（Text-First）**、Markdown/YAML 导出、一键重建 |

## 3. 金币、战力和其他动态数据

### 3.1 不要只保存“当前值”

不建议只保存：

```yaml
character: hero
gold: 120
```

这种数据无法回答“为什么是 120”“第 5 章是多少”“删除一场交易后怎么办”。更稳定的做法是保存定义、变化事件和可重建快照：

```text
指标定义：gold，单位为 coin，整数，允许为 0
事件：任务奖励 +200，发生于 chapter-2
事件：购买药剂 -80，发生于 chapter-3
快照：chapter-3 结束时为 120（由上述事件计算）
```

### 3.2 三层数据

#### 指标定义 `metric_definition`

描述“这个数值是什么”：

- 名称和别名；
- 数据类型：整数、小数、范围、枚举、未知；
- 单位和精度；
- 是否允许负数；
- 适用项目、世界线和版本；
- 显示规则。

#### 状态变化事件 `state_event`

描述“发生了什么变化”：

- 事件类型：获得、消耗、转移、伤害、恢复、升级、解锁、失效；
- 主体和对象；
- 变化量或新值；
- 故事时间和场景定位；
- 原文、草稿或项目设定来源；
- 是否是正式事件、候选事件或推测事件。

#### 状态快照 `state_snapshot`

描述“在某个时间点计算出来的结果”。它是派生数据，必须记录：

- 所依据的事件版本；
- 使用的规则版本；
- 计算时间；
- 是否新鲜；
- 是否存在未知或冲突事件。

快照过期后重算，不能当成独立事实。

### 3.3 战力不能强行压成一个数字

“战力”可能同时包含攻击、防御、速度、控制、资源、情报、环境适应和临场状态。建议保存：

- 基础能力；
- 装备和增益；
- 伤势、疲劳、限制和环境；
- 计算公式或规则集版本；
- 评估时间；
- 评估来源和不确定性。

如果原作只说“实力很强”，不要自动伪造精确数值。可以保存为区间、等级、相对比较或“未知”。

### 3.4 规则属于项目，不属于全局事实

同一个“战力”在不同作品或 AU 中可能定义不同。计算公式应绑定 `project_id`、`world_id` 和 `rule_revision_id`，放在 `rules-calculation` 模块；知识库只保存规则版本及计算结果，`novel-Skill` 负责在正文写作时查询结果。

### 3.5 推荐查询

```text
state_at(project_id, entity_id, story_time, metric_id)
ledger(project_id, entity_id, metric_id, from_time, to_time)
explain_state(snapshot_id)
check_state(draft_id, scene_id)
```

这些查询默认只读。修改正文中的交易、战斗或能力变化，应产生新的草稿事件或项目事件，而不是手动覆盖旧快照。

### 3.6 半途接入与“三态数值”演进方案（写到第50章突然想加金币/战力）

长篇连载最常见的场景是：**作者前 50 章完全没有统计金币/战力，写到第 51 章主角买灵草花了 500 灵石，作者突然希望系统从此开始精确跟踪余额。**

如果系统要求“凡是数值必须从第 1 章开始有初始值 0”，那么第 51 章直接 -500 必然触发“余额透支”的致命报错；如果逼迫作者回头逐章补录前 50 章的花销，作者必定放弃使用。

系统通过**三态数值模型**与**基准锚点**实现无损演进：

1. **三态数值（Three-State Value）**：
   - `EXPLICIT`（显式精确值）：由完整的变动事件链计算得出；
   - `UNMEASURED`（未测量/未知）：该时段内作者尚未开始跟踪该指标。系统在此区间不做透支断言，不报异常；
   - `NOT_APPLICABLE`（不适用）：非当前世界的属性（如修仙世界查“魔法值”）。
2. **基准锚点事件（`baseline_anchor`）**：
   - 作者无需补录前 50 章，仅需在第 51 章前登记一个 `baseline_anchor` 事件：`entity_id: lin_dong, metric_id: spirit_stones, value: 3000, story_time: chapter_51_start`；
   - 系统从此时间点开始向前冻结为 `UNMEASURED`，向后则按 3000 为起点进行严格的加减结算（51 章买药 -500 后结余 2500）；
   - 若未来作者有闲暇回头补录了第 20 章获得 10000 灵石，系统支持设置“区间局部账本”，不强制两个不同阶段的账目必须绝对贯通。

## 4. 风格学习效果差时怎么办

### 4.1 先区分问题来源

生成效果差不一定是“模型不会写”，至少可能来自：

1. 找错了范例；
2. 风格标签不准确；
3. 风格档案版本过时；
4. 项目要求和共享风格冲突；
5. 当前场景、人物认知或目标不完整；
6. 提示词拼装顺序不合理；
7. 模型能力不足；
8. 评估标准本身没有明确。

因此每次生成最好保存一个可复现的 `generation_context`：项目 revision、风格档案版本、检索结果 ID、提示词版本、模型和参数。这样才能判断是检索、上下文、提示词还是模型的问题。

### 4.2 风格资料必须可停用和回滚

风格档案、范例和标签都应有生命周期：

```text
candidate → active → disabled
             │          │
             └→ revised ─┘
```

“删除某条风格知识”通常先表示“不再参与默认检索”，而不是立即物理删除。保留版本可以比较删除前后的效果；确实需要永久删除时再执行带影响报告的清理。

### 4.3 用小型评测集代替主观记忆

每个项目可保存少量固定测试场景：

- 同一个角色的对话；
- 紧张、悲伤、战斗和日常场景；
- 原作口吻约束；
- 项目禁止事项；
- 用户改写后的优选示例。

更换风格档案、embedding、提示词或模型后，用同一组场景比较。评测结果可以是用户评分、规则检查和人工备注，不必一开始追求一个虚假的“文风准确率”。

### 4.4 不要自动训练成不可逆状态

用户反馈可以先保存为 `style_feedback` 或 `evaluation_record`。只有用户确认的反馈才能升级为风格规则或范例。否则一次偶然不满意的生成可能永久污染后续结果。

### 4.5 反面教条（anti-pattern）强约束注入

模型在生成网络小说时极易滑向“油腻堆砌词藻”、“反派话多自报家门”、“打斗动作虚化”等典型坏味道。
系统不仅支持正面学习，更支持定义**负面反面范例（`anti_pattern`）**：
- 在风格档案中声明 `anti_pattern` 约束规则（如“动作描写严禁连续使用三个成语”）；
- 上下文装配器在生成正文 Prompt 时，自动将这些负面禁令转化为 Negative Constraint，迫使模型避开恶习。

### 4.6 Canary 金丝雀试跑与一键熔断

新提炼的风格规则或微调范例，严禁直接对全书生效：
- 新版本先置为 `canary` 状态，仅在作者指定的 1~2 个独立试写草稿中分流注入；
- 若试写体验不佳或被作者标记差评，系统一键执行 `disable`，立即无损熔断并退回原稳定版本。

## 5. 删除、替换和停用必须分开

“删除内容”至少有四种含义：

| 操作 | 含义 | 是否可恢复 |
|---|---|---|
| `exclude` | 不参与当前查询 | 是 |
| `disable/archive` | 暂停使用但保留历史 | 是 |
| `supersede` | 被新版本替代 | 是 |
| `purge` | 永久删除原文及派生副本 | 通常不可恢复 |

默认只做 `exclude`、`disable` 或 `supersede`。永久删除前必须：

1. 生成备份或确认已有备份；
2. 展示引用它的主张、项目、范例、提议和索引；
3. 让用户选择级联处理、保留孤立引用或中止；
4. 删除或重建相关派生数据；
5. 记录操作结果。

原始来源、正式主张、项目设定和草稿的删除策略可以不同，不能共用一个“删除条目”命令。

## 6. 新增数据和流程如何保持兼容

### 6.1 数据模型版本化

每个持久化记录和导出文件应有 `schema_version`。新字段优先采用向后兼容的添加方式：

- 旧字段继续可读；
- 新字段可选并有明确默认行为；
- 删除字段前先标记 deprecated；
- 迁移必须可测试、可回滚或可从备份恢复；
- 不让业务代码依赖数据库内部列名。

### 6.2 API 版本化

API 使用 `/v1`。破坏性变化进入 `/v2`，不要悄悄改变 `/v1` 的含义。新增结果字段通常兼容，但客户端必须忽略未知字段；删除字段、改变状态含义或改变默认 scope 都属于需要迁移的变化。

### 6.3 类型注册而不是到处写死分支

未来新增“任务点”“声望”“污染值”“关系亲密度”等指标时，应注册新的 `metric_type` 或 `state_event_type`，而不是修改所有查询代码。未知类型至少可以作为普通记录保存和展示，不能因为旧程序不认识就丢弃。

### 6.4 算法和模型版本化

以下内容都必须单独命名和记录：

- 解析规则版本；
- 切片规则版本；
- embedding 模型和维度；
- 重排模型；
- 摘要/抽取提示词版本；
- 状态计算规则版本；
- 风格评测规则版本。

新版本建立新索引或新结果集，验证后再切换默认版本；不要覆盖旧结果到无法比较。

## 7. 生成结果的可复现快照

为了判断“为什么这次效果变了”，每次重要生成或检查应能引用：

```yaml
generation_context_id: gc-001
project_revision: 18
source_revisions: [source-a:7, draft-1:12]
claim_versions: [claim-22:3]
timeline_id: main-line
style_profile_revision: style-default:5
retrieval_request_id: req-123
retrieval_index_version: hybrid-2026-09
prompt_version: novel-context-v2
model: local-model-x
```

这不是为了永久保存所有模型输出，而是为了在需要排错时知道生成依据。原始草稿是否长期保留由项目策略决定。

## 8. 还容易被忽略的场景

### 8.1 不确定和缺失值

“未知”“没有”“尚未确认”“不适用”不是同一个状态。数值也可能是精确值、区间、下限、上限或角色估计。否则系统会把缺失信息当成零。

### 8.2 别名、翻译和实体合并

同一角色可能有真名、化名、译名和昵称；不同角色也可能同名。实体合并必须产生候选关系并保留证据，不能仅按字符串自动合并。

### 8.3 反向揭示和不可靠叙事

“当时角色说了什么”和“世界真实发生了什么”要分开。时间线允许后续证据改变解释，但不能修改过去的原始对白。

### 8.4 分支世界线和重置

平行世界、时间回溯、重写章节和不同结局应使用 branch 或 timeline 分支。共享内容只读继承，分歧内容在分支中保存。

### 8.5 崩溃、重复导入和半完成任务

导入和分析任务要有 `job_id`、幂等键和状态：`queued`、`running`、`completed`、`failed`、`cancelled`。重试不能重复创建同一 revision、事件或主张。

### 8.6 外部模型和隐私

发送给外部 API 前要知道：

- 哪些来源允许外发；
- 是否需要脱敏；
- 使用了哪个 provider 和模型；
- 外部分析结果是否允许回写；
- 网络失败时是否明确报错。

API key 和隐私策略属于配置/运行层，不属于知识内容。

### 8.7 大资料和性能退化

资料增长后可能遇到导入慢、索引膨胀、查询上下文过大和备份时间变长。要保留分页、增量索引、按项目分区、上下文预算和重建进度，不要在第一版就把所有内容一次性送给模型。

### 8.8 数据出口和长期可维护性

必须能在不依赖特定模型、向量数据库或 UI 的情况下导出：

- 原始 txt/md；
- Markdown 结构化条目；
- JSON 主张、对象、事件和项目关系；
- SQLite 备份；
- 可选的索引重建清单。

### 8.9 合法“吃书”（Retcon）的追溯性修正演进

长篇小说创作往往历经数月甚至数年，作者推翻早期设定（如第 10 章设定某神剑为玄铁打造，第 60 章因构思变动改为“其实是上古真龙骨骼所化”）是家常便饭。
系统不能简单把这种行为当成“逻辑错误”死板拦截：
- 引入显式 `retcon` 追溯性修正事件：声明 `superseded_claim_id`（旧主张）、`new_claim_id`（新主张）及 `narrative_order`（在哪个叙事节点生效）；
- OOC 检查引擎检测到关联的 `retcon` 声明后，自动对后续章节豁免冲突报警；
- 写作上下文装配器自动在 `novel-Skill` 提示中注入“吃书过渡提醒”（如：提示作者在此处添加‘世人皆以为是玄铁，实则当年真龙陨落...’的叙事遮掩），帮助作者圆场。

### 8.10 物理章节增删与语义场景 UUID（Scene UUID）

作者在连载期间常遇到“在第 15 章与第 16 章之间加更一章过渡戏”的情况。如果系统以物理文件或章号（如 `chapter_15.txt`）作为因果、伏笔与金币账本的锚点，一旦插入章节，后续所有章号整体自增，将导致全书成百上千条伏笔与账本索引全部断链错位。
- 核心设计：**全面使用不可变的语义场景 UUID（`scene_uuid`）作为底层时序与因果关联键**；
- 物理章节序号仅作为展示层视图（由文件行号或目录树动态解析计算），即便作者随意插章、删章或互换章节顺序，底层引用关系牢不可破。

### 8.11 视点盲区与防止偷看剧本（POV Observer Filter）

群像小说写作经常切换视角（如从主角视角切换到反派潜伏视角）。如果系统检索全书信息时不区分视点，就会把主角刚刚在密室藏匿法宝的暗线设定注入到反派视角的写作 Prompt 中，导致模型替反派写出“他早已看穿主角在密室藏了重宝”的荒谬穿帮。
- 检索接口强制支持 `pov_character_id` 参数；
- 检索过滤链路校验 `character_knowledge` 认知状态，凡观察者在当前客观时间与叙事释放点尚未获知的信息，一律物理剪除，严保叙事悬念与戏剧张力。

### 8.12 本地硬件显存红线与云端成本控制（RTX 2060 6GB）

创作者本地配备 RTX 2060（6GB VRAM）。系统必须在架构上彻底规避“本地同时常驻大语言模型与向量模型导致显存溢出卡死”的问题：
- **本地常驻层**：仅运行轻量级 Qwen3-Embedding-0.6B（FP16 显存占用约 1.5GB），专门用于极速文本向量化与语义相似度初筛，断网亦可顺畅工作；
- **云端弹性层**：长篇大段的世界观抽取、OOC 深度逻辑校验与正文辅助生成，委托给超低成本、大上下文的云端 API（如 Gemini Flash / DeepSeek）；
- **上下文 Token 预算**：将单次生成的提示词严格裁剪至 2500~4000 tokens 黄金区间，既保护了注意力焦点（防止 Lost-in-the-Middle 遗忘关键情节），又将长期 API 成本降低 70% 以上。

## 9. 建议新增的模块

现有模块之外，后期应预留但不必马上实现：

| 模块 | 作用 | 第一版边界 |
|---|---|---|
| `state-ledger` | 金币、资源、能力、伤势和关系的变化事件 | 先支持通用数值和事件，不做完整游戏引擎 |
| `rules-calculation` | 战力、资源结算和项目规则版本 | 只提供可解释计算，不自动创造规则 |
| `quality-evaluation` | 风格评测、检索评测和回归样例 | 先支持人工评分和固定案例 |
| `lifecycle` | 排除、停用、替代、删除和影响分析 | 默认可恢复 |
| `compatibility-ops` | schema/API 版本、迁移、备份、恢复和能力发现 | CLI 优先 |
| `job-runner` | 导入、解析、分析、索引的异步任务 | 先保证幂等和失败可见 |

其中 `state-ledger` 和 `quality-evaluation` 是本次规划发现的两个重要缺口；如果现在完全不预留，后期很可能需要重做主张、时间线和 API。

## 10. 分阶段实现建议

### 阶段 A：先冻结数据边界

- 统一 ID、scope、revision、status 和 source reference；
- 定义 query/propose/commit/admin 权限；
- 定义导出格式和 API 错误契约；
- 建立一组冲突、时间线和项目隔离测试数据。

### 阶段 B：实现可靠核心

- 原始来源和文档片段；
- 项目/世界线隔离；
- 对象、主张、证据和历史；
- FTS5、CLI 和只读 API；
- 备份、恢复和冲突清单。

### 阶段 C：加入动态状态

- 事件账本；
- 时间点状态查询；
- 金币、物品、能力和关系变化；
- 可解释的基础计算规则；
- 草稿状态检查。

### 阶段 D：加入风格质量闭环

- 风格档案版本；
- 范例和负面范例；
- 固定评测场景；
- 生成上下文快照；
- 用户反馈、停用和回滚。

### 阶段 E：再扩展模型和工具

- embedding 版本并存；
- 本地/外部模型 provider；
- 异步任务；
- HTTP 适配层或未来 UI；
- 插件化解析器和检查器。

## 11. 不能保证完全兼容的地方

有些变化即使设计良好也会改变结果，必须接受“可迁移但不完全相同”：

- 更换 embedding 模型会改变排序；
- 更换大模型会改变摘要、风格分析和推测；
- 修改切片规则会改变检索上下文；
- 修改计算公式会改变历史战力结果；
- 用户确认新的项目设定会改变旧章节的检查结果。

系统应保证的是：原始资料不丢、旧版本可追溯、变化原因可解释、旧结果可以复现或标记为过期，而不是保证不同模型永远返回完全相同的文本。

## 12. 最低验收标准

后期扩展前，至少应能通过以下检查：

- 删除一个风格条目后，默认检索不再返回它，且可以恢复；
- 原文新增一版后，旧主张仍可追溯，旧索引标记过期；
- 三个项目可以有同名角色但互不串数据；
- 删除一笔金币交易后，可以重算指定章节的余额；
- 修改战力规则后，旧计算结果仍标记原规则版本；
- AI 生成的错误主张不会自动进入正式知识；
- 更换 embedding 后，可以并存旧索引并比较结果；
- API 旧客户端遇到新字段仍能工作；
- 导入任务失败后可以重试而不产生重复数据；
- 从导出文件可以恢复核心资料和项目关系。

## 13. 最终判断

为了兼容未来使用场景，知识库不应只是“文档 + 向量搜索”，而应至少预留四种能力：

```text
证据与主张管理
项目/时间线隔离
事件驱动的动态状态
可评测、可回滚的派生结果
```

但这不意味着第一版要做成复杂的游戏引擎、自动训练系统或全能 Agent。先冻结边界和版本机制，再以通用事件、状态查询、风格评测和生命周期管理逐步扩展，后期才不会因为一个新场景而推倒重来。
