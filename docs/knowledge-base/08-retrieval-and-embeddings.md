# 08 检索、中文分词、POV 视线过滤与场景剪枝

> 状态：`CURRENT + PLANNED`
> **当前实现状态**：中文 FTS5、能力驱动问答计划、来源/时间线范围和 ContextPruner 的 POV 剪枝已可用；embedding、向量数据库和 RRF 混合重排仍是规划项，不应按本设计文档的模型清单判断为已安装能力。

## 这一部分用来做什么

它负责在作者写作或 `novel-Skill` 发起请求时，根据 **当前项目 + 查询意图 + 故事时间点 + 叙述视角 (POV) + 场景类型**，精准召回所需材料，并完成上下文体积剪枝：

- 原著原文、章节与对话上下文；
- 故事世界实体当前状态；
- 项目当前私有设定与 AU 规则（含分歧点 POD 过滤）；
- 角色当前认知与 POV 视角盲区物理隔离；
- 文笔风格范例、负向禁写范例与创意素材。

## 中文检索基线：FTS5 分词暗礁与专有词典方案

### 1. 为什么原生 SQLite FTS5 会在中文写作中失效？
SQLite 内置的 `unicode61`、`ascii` 分词器无法识别中文词语边界，默认会把一段汉字切成单字或整个长串。这导致：
- 搜“陆沉”（人名），会误召回所有出现“大陆”、“沉思”的无关段落；
- 搜“大罗天征”（自造武学），单字切分导致召回率极低或噪点极高。

### 2. 解决方案：应用层结巴分词 + 项目专有词典（Project Lexicon）
采用最稳妥、跨平台零 C 编译依赖的落地方案：

```text
文档切片文本 (Chunk Text)
    │
    ▼
Python jieba 分词引擎 ◄── 加载 [动态项目专有词典 Project Lexicon]
    │                     (自动提取人物名、别名、宗门势力、功法法宝)
    ▼
空格拼接的 Token 串
    │
    ▼
写入 SQLite FTS5 虚拟表 (采用 unicode61 或 simple 模式快速索引)
```

- **增量响应零卡顿**：草稿保存时仅触发 CPU 结巴分词与 FTS5 写入，耗时 < 10 毫秒；
- **动态专有词典热加载**：每次向知识库添加人物实体、法宝物品或项目专有名词时，自动触发更新 `project_lexicon.txt`，切词准确率达 100%。

## 本地 Embedding 模型与硬件适配

| 模型 | 本地/云端 | 规格 | 硬件表现 (i7-10750H, 40GB RAM, RTX 2060 6GB) | 定位 |
|---|---|---|---|---|
| **Qwen3-Embedding-0.6B** | 本地 | 0.6B, 1024 维, 32K 上下文 | 中文语义最强，支持指令引导；GPU FP16 占 ~1.5GB 显存，batch 1~4 运行顺畅 | **首选候选** |
| **BAAI/bge-m3** | 本地 | 0.6B, 1024 维, 8K 上下文 | 生态成熟，支持 dense/sparse/ColBERT；显存占用略大 | **稳妥对照基线** |
| **EmbeddingGemma-300M** | 本地 | 300M, 768 维, 2K 上下文 | 轻量，但激活不支持 float16，老显卡建议 CPU 运行 | **轻量备选** |
| **Gemini Embedding** | 云端 API | 2048 tokens, 128~3072 维 | 质量高但数据离境，网络依赖，无法断网运行 | **仅作云端对照** |

> **算力调度原则**：切片严格控制在 512~1024 字符。向量计算放入**异步闲时队列（Idle Worker）**，绝不阻塞当前写章节的心流。

## 混合检索流水线（含 POV 视线过滤）

```text
用户 / novel-Skill 查询请求 (含 project_id, story_time, scene_type, pov_character_id)
    │
    ├── 1. 作用域硬性过滤 (强制隔离其他项目、未 link 资料及分歧点 POD 后原著动态情节)
    │
    ├── 2. FTS5 中文全文召回 (基于专有词典，负责抓精准人名、地点、对话原句)
    │
    ├── 3. 本地向量语义召回 (基于 Qwen3-Embedding，负责抓情绪、氛围、隐含行为)
    │
    ▼
倒数互惠排名融合 (RRF: Reciprocal Rank Fusion)
    │
    ▼
4. POV 视线盲区物理过滤 (凡在 pov_character 眼中属于 unknown/hidden 的秘密一律剔除)
    │
    ▼
5. 场景化上下文剪枝 (Context Pruning, 限制在 2500~4000 tokens 甜点区)
    │
    ▼
输出精准证据包 (Context Evidence Pack)
```

当前实现中，上图第 3～4 步（向量召回和 RRF）尚未接入生产调用链。问答实际走
`QueryEngine → RetrievalPlanBuilder → ChineseFTS/领域只读读取器`，返回能力级
`evidence_blocks`；没有明确 source/timeline/provenance 的结果只可标为
`INCOMPLETE` 或 `LEGACY_HINT`，不会被当作权威事实。写作请求仍必须单独经过
`ContextPruner` 的 POV、knowledge/source version 和预算门。

## 场景化上下文剪枝策略（Context Pruning）

大模型上下文塞入无关注释会导致严重的注意力漂移（Lost-in-the-Middle）。检索系统根据调用方传入的 `scene_type` 进行**场景化精简**，严格控制在 **2500 ~ 4000 tokens 黄金预算区**：

### 1. 战斗场景（`combat`）
- **高优先级保留**：双方当前可用技能、冷却、法宝耐久、伤势状态（来自 `state-ledger`）、地形障碍；
- **强力剪枝**：剔除长篇环境渲染文风、无关人物情感纠葛、遥远的历史设定。

### 2. 谈判与暗战对白场景（`dialogue`）
- **高优先级保留**：双方认知盲区（`knowledge_state`）、各自伪装身份、隐藏动机、潜台词对话范例与负向禁写范例（来自 `materials-style`）；
- **强力剪枝**：剔除战力数值、装备属性明细。

### 3. 过渡与日常场景（`transition`）
- **高优先级保留**：环境描摹技巧、节奏控制范例、角色口头禅风格档案；
- **强力剪枝**：压低规则设定约束。

## 评测基准（Benchmark）

通过本地预设的 30~50 个真实写作查询用例进行比对：
- **精确事实用例**：如“艾琳在黑石城堡获得的武器名字”；
- **语义意图用例**：如“充满压迫感但双方未拔刀的对峙场面”；
- **AU 隔离用例**：同名角色在项目 A 与项目 B 的设定召回准确率；
- **防 OOC 与 POV 盲区用例**：反派视角是否成功过滤主角藏匿的秘密。
